# Effect v4 capability index for Bridger and an ERP platform

Research date: 2026-10-02. Scope: API and architecture research, with 45 discoverable capabilities. This is a broad inventory, not a claim to enumerate every API. ERP uses below are design proposals, not capabilities supplied automatically by Effect.

## Version and evidence baseline

The canonical repository is now **Effect-TS/effect, branch main**. Its package metadata reports **4.0.0**; the v4 documentation announces 4.0. The former effect-smol repository explicitly says it is archived and v4 moved to the canonical repository; v3 lives on the `v3` branch. Therefore the old effect-smol `4.0.0-beta.98` metadata is historical, not the current baseline. [Current package](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json), [v4 documentation](https://effect.website/docs/v4/onboarding), [repository move](https://github.com/Effect-TS/effect-smol).

Do not copy `effect/unstable/*` or `effect/unstable/httpapi` paths from beta examples. An ordinary-looking path does not establish stability: many modules now carry `@stability unstable` in source. Some web cache entries lag current source, so the package export map controls import-path conclusions. After the Context7 connection was completed, the Effect lookup succeeded. Context7 corroborated E06–E08: LayerRef invalidation leaves existing scoped borrowers valid until their scopes close; LayerMap provides keyed scoped service families and invalidation. [LayerRef reference](https://www.effect.website/docs/v4/api/effect/LayerRef), [LayerMap reference](https://www.effect.website/docs/v4/api/effect/LayerMap), [RcRef reference](https://www.effect.website/docs/v4/api/effect/RcRef).

Maturity labels: **Core** means public core export without an unstable annotation observed for the capability; **Unstable** means an explicit source annotation; **Verify** identifies a narrower unresolved compatibility question. Core does not imply every function or every downstream adapter is stable.

**Accepted policy:** the user permits all Effect v4 unstable features. Every capability below is eligible for the design; instability does not require additional approval or waiting for a stable release. Version and compatibility notes remain engineering inputs.

## Design consequences for Bridger

These are proposed conclusions from the inventory, not additions to the public API yet.

1. **Keep host ownership explicit.** Use E02–E05 for service construction and lifetime. Evaluate E06–E09 as implementation primitives. Bridger still owns provider selection, runtime manifest checks, readiness, dependency reactivation and removal semantics.
2. **Make activation generations visible internally.** A captured service belongs to a particular generation. Admission closes before draining; existing borrowers retain that generation until release. LayerRef's documented behavior provides useful support for this model, but does not implement the complete protocol.
3. **Offer observable host state through a small generic contract.** E16 fits the core snapshot/change seam. React/FoldKit adapters should not need the unstable atom subsystem simply to display plugin availability.
4. **Use unstable modules where they fit.** SQL, durable execution, HTTP, RPC, atoms and the other unstable capabilities are approved design options. Organize adapters by responsibility and version dependencies explicitly. Keep the minimal plugin lifecycle contract generic because of its purpose, rather than excluding APIs based on maturity.
5. **Treat code installation, activation and business upgrade as different operations.** Dynamic import can make approved code available. Activation builds scoped services. A business upgrade may alter persistent data and outstanding workflows; it needs a separate versioned procedure.
6. **Do not infer hot mutation from Layer composition.** Existing effects can retain service values captured earlier. Replacing a registry entry does not rewrite those values. Both dependent reactivation and call leases need a specified host contract.

## Transaction and durability boundaries

| Boundary | Candidate Effect capability | What the application must specify |
| --- | --- | --- |
| Atomic host state in one process | E13–E14 | Registry invariants and notification consistency. |
| Atomic records in one database transaction | E29 | Tenant constraints, isolation, optimistic versions and uniqueness. |
| Database change plus external message | E29 + an application outbox | Atomic outbox write, dispatcher retries, deduplication and reconciliation. |
| Human approval or long-lived process | E33–E36 | Durable engine, schema/code versioning, correlation and compensation policy. |
| Multiple server workers | E37 | Ownership, storage backend, restart behavior and upgrade compatibility. |

None of these boundaries implies an automatic transaction spanning all of them. A correct invoice-posting example must identify its commit point, its idempotency key and how the caller resolves an ambiguous result.

## Questions to resolve before implementation

- Pin exact versions of Effect, FoldKit, Alchemy and every platform/SQL adapter, then type-check a tiny compatibility fixture. These live-source observations do not prove they can all be installed together.
- Specify the plugin ABI: manifest schema, service identity, compatibility ranges, exported entry point, required runtime dependencies and module duplication policy.
- Specify removal with active SQL transactions, streams and workflow handlers. Decide which operations drain, reject, resume under the old version, or require an explicit migration.
- Select tenant isolation and database ownership before deriving repositories or cache keys. Effect Context is dependency provision, not a security sandbox.
- Choose one durable command/idempotency/outbox strategy before promising reliable integration delivery.
- Validate decimal rounding and date-only models against actual accounting requirements. E25–E26 provide mechanics, not jurisdictional rules.
- Measure the need for E24 schema compilation, E37 clustering and E38 event synchronization. Their existence does not make them mandatory architecture.
