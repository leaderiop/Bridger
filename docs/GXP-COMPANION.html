Section 1

Five words you'll meet

Regulated software has its own vocabulary. These five terms come up on almost every page of this guide, so here they are in plain language first.

GxP

"Good practice" rules

The family of rules for regulated industries: GMP for manufacturing, GLP for laboratories, GCP for clinical trials. When software touches a regulated process, it falls under these rules too. In the US the key text for software is 21 CFR Part 11; in Europe it is EU GMP Annex 11.

Audit trail

The diary of every change

A record, written as things happen, of who changed what, when and why. Records are only ever added; nothing is edited or deleted. An inspector reads it to reconstruct the history of the system.

E-signature

A signature on a screen

The electronic equivalent of signing a paper form. It identifies the person, records the date and time, and states its meaning, such as "approved" or "reviewed". Part 11 sets strict rules for it.

IQ · OQ · PQ

Proving the software works

Validation evidence comes in three layers. IQ: the right software is installed correctly. OQ: it behaves as its specification says. PQ: it does the job in your real process. A supplier can help with IQ and OQ. PQ is always the user's.

Port and adapter

A socket and a plug

A port is an interface the core calls without knowing who answers, like a power socket. An adapter is the plug you build for it, for example code that writes audit records into your own database.

Section 2

The problem: changing software in a regulated plant

Bridger is a plugin host. A business application runs on top of it, and features arrive as plugins: a plugin that reads a laboratory balance, one that prints batch labels, one that talks to a dosing pump. Plugins can be installed, replaced, reconfigured and removed while the application runs.

In an ordinary company that flexibility is simply convenient. In a pharmaceutical plant it is a change to a validated system. If a plugin that reads the balance is swapped for a different version, the weights recorded in a batch might change, and so might a patient's dose. Every such change therefore has to be controlled and explainable, years later, to an inspector.

An inspector looking at any change will ask the same four questions:

Who did it?

A named, authenticated person, never "the system" or "admin".

What, when and why?

A trustworthy, ordered record with a time and a reason for each change.

Was it approved?

Where your procedures say so, a second person signed off before it happened.

Can you prove it works?

Evidence from real test runs that the software does what its documents say.

Section 3

What the core already does

The Bridger core, @bridger/core, is specified (not yet built) to answer part of those questions by itself. Every change to the plugin set passes through the same eight checks inside the host, always in the same order. Two of those steps are deliberately left open: the core calls out to something else and waits for the answer. These are the places where the companion plugs in.

Rule 1: no record, no change

If the core cannot record that a change was requested, the change does not happen. The call fails with AuditUnavailable. This is called failing closed.

Rule 2: the audit alarm

If the outcome of a change cannot be recorded, the core turns on an alarm (the "latch"). Until a person acknowledges it with a reason, no further operator changes are accepted.

Rule 3: silence means no

If the gate crashes or does not answer within its time limit, the change is refused. A broken approval system can never wave changes through.

The two open steps are defined as ports. In code they are small interfaces: one to send a record somewhere, and one to ask whether a change may happen.

Specified in the core · behaviours 23 and 25// Where records go. The core calls this for every record, in order.
interface AuditSink {
  readonly record: (r: AuditRecord) => Effect.Effect<void, AuditWriteFailed>
}

// Whether a change may happen. The core calls this before recording anything.
interface OperationGate {
  readonly authorize: (req: OperationRequest) => Effect.Effect<void, OperationRejected>
}

// What the gate is shown about the change.
interface OperationRequest {
  readonly operation: Operation          // "install", "replace", "remove", ...
  readonly target?: { id: string; realm: string }
  readonly actor: Actor                  // who is asking
  readonly reason?: string               // why
  readonly correlationId: string         // links the request, its records and any signature
  readonly definition?: { version?: string; digest?: string }
  readonly configChange?: { paths: readonly string[] }   // which settings, never their values
}
Section 4

Why a companion package?

The core stops at the ports on purpose. It produces the records and offers a place to ask for approval, but it keeps nothing and signs nothing. Once the sink has accepted a record, the core forgets it. This table shows what is still missing once the core has done its part.

The inspector asksThe core givesStill missing
Who did it?An actor on every change; anonymous calls can be refusedProof that the actor is a real, logged-in person
What, when and why?Numbered, time-stamped records with a reasonSomewhere safe to keep them
Is anything missing?A function that checks the numberingA routine that runs it over the stored trail
Was it approved?The gate, called before anything happensA gate that actually collects an approval and a signature
Which setting changed, and to what?The names of changed settings, never their valuesA safe way to compare values without revealing them
Can you prove it works?A specification and a planned test suiteIQ/OQ documents produced from a real test run

So something has to fill the gaps. There are three ways to do it, and only one of them holds up.

Rejected

Build it all into the core

Every plant uses a different database, a different login system and a different way to sign. Building all of that into the core would load it with dependencies that most users never need, and it would tempt the core into "helpful" defaults. An in-memory audit store would vanish on restart. A placeholder signature would approve everything.

Rejected

Leave it to every team

Each regulated team would rediscover the same tricky rules alone: why a retried record must not be stored twice, why a sink must never report a save it did not make. Each would also write validation evidence in its own format. That costs more, and it is harder for inspectors to compare.

Chosen (ADR-BR-034)

A separate, optional companion

One package, @bridger/gxp, that depends on the core while the core never depends on it. It defines the contracts and tests once, captures approvals through the gate, and produces evidence. Teams that are not regulated simply don't install it. The same split already worked for Bridger's sister project Qadi and its @qadi/audit companion.

Section 5

How the companion will work

The companion has five parts, listed in decision ADR-BR-034. Each is explained below in the same order: the problem in plain words, a diagram, how it works, a code sketch, and what it cannot do. The code shows the intended shape, but every companion name in it is a proposal until the specification is written.

1

A contract for writing the audit trail

The core sends each record to an adapter that you write for your database. The companion is to set out the rules a good adapter follows, and ship tests that prove yours does.

Why does an adapter need rules? Because things go wrong in the middle. Imagine the database is slow. The core waits, gives up after a timeout, and sends the same record again, with the same identifier and the same sequence number. If the first write did land after all, a careless adapter now stores the record twice. Worse, an adapter that hides a database error and reports success makes the core believe a record exists when it does not.

The rules the contract is expected to contain:

  • Store each record once. Writing the same recordId twice must change nothing.
  • Never fake success. Any write that cannot be confirmed must fail with AuditWriteFailed.
  • Keep every field. Records are stored exactly as given, including their format version.
  • Only add. The adapter never edits or deletes a stored record.
  • Order by number. Records are read back in sequence-number order, never by timestamp, because clocks can jump.

  record: (r) =>
    sql`insert into audit_trail (record_id, host_id, audit_seq, body)
        values (${r.recordId}, ${r.hostId}, ${r.auditSeq}, ${JSON.stringify(r)})
        on conflict (record_id) do nothing`          // a retry is harmless
      .pipe(
        Effect.asVoid,
        Effect.mapError((e) => new AuditWriteFailed({ message: String(e) }))  // report failure honestly
      )
})

What it cannot do

The companion writes the rules and the tests. It does not store anything itself. Keeping records safe for years, backups, access control and retention belong to your database and your IT. Neither package claims to store records durably.

2

Checking the stored trail

Every record gets a number from the host: 1, 2, 3, and so on, without gaps. If a number is missing or appears twice in your database, something went wrong on the way. The companion is to run that check over the stored trail and produce a report a reviewer can file.

verifyAuditSequence is specified in the core · the loading code is illustrativeconst stored = yield* trail.load({ hostId: "line-3-host" })
const report = verifyAuditSequence(stored)
// → { gaps: [{ after: 2209, before: 2211 }], duplicates: [2211], outOfOrder: [] }

What it cannot do

It finds lost and repeated records, but it is not tamper evidence. Someone who can rewrite your database can also renumber the records neatly. Nor can it notice that a whole trail is gone, or that the newest records after the last stored one were lost. Protecting the database itself is your job.

3

Approvals and electronic signatures

Many changes need a second person's sign-off before they happen. The core offers the gate as the place to ask. The companion is to supply a gate that insists on an approval for chosen operations, while you supply the part that actually identifies the signer.

Part 11 §11.50 says a signed record must show the signer's printed name, the date and time, and the meaning of the signature: review, approval, responsibility or authorship. Identifying people safely depends on your login system, so signature capture is a port you implement. There is deliberately no default, not even a "do nothing" version, because a fake signer would quietly approve everything.

Approvals usually happen before the change, sometimes hours before, so the guide shows the likely design: an approval ticket is signed first and the change refers to it later. Section 8 explains why this is still an open question.

Illustrative · proposed shape, nothing specified yet// You implement this: it knows how your company identifies people.
interface SignatureCapture {
  readonly capture: (req: OperationRequest, meaning: "approval" | "review")
    => Effect.Effect<SignatureRecord, SignatureRefused>
}

// The companion supplies the gate; you choose which operations need approval.
const gate = Gxp.approvalGate({
  operations: ["install", "replace", "remove", "reconfigure"],
  signatures: ssoStepUp,                       // required: there is no default
})

// Wiring: give the host your gate and your audit adapter.
const host = yield* Bridger.make(options).pipe(
  Effect.provideService(OperationGate, gate),
  Effect.provideService(AuditSink, postgresSink(sql)),
)

What it cannot do

It does not log anyone in, does not make a signature legally binding, and does not provide the identity controls of Part 11 §§11.100–11.300. Those depend on your systems and procedures.

4

Fingerprints for configuration values (optional)

The core never puts setting values in the audit trail, only the names of the settings that changed. That keeps passwords and connection strings out of the trail. Sometimes an auditor still needs to know whether a value went back to what it was before. A fingerprint answers that without revealing the value.

A fingerprint is a keyed hash (HMAC) of the value, made with a secret key. Equal values always give equal fingerprints and different values give different ones, but the fingerprint cannot be turned back into the value without the key.

What it cannot do

It needs a secret key that someone manages and rotates. It also cannot hide short or guessable values: if a setting can only be true or false, anyone can hash both and compare. The specification must say which fields may be fingerprinted, which is why the feature is optional and lives outside the core.

5

IQ/OQ evidence from real test runs

To validate a system that includes Bridger, a regulated user needs documents showing that Bridger is installed correctly (IQ) and behaves as specified (OQ). The companion is to produce them from an actual run of Bridger's acceptance tests on the installed package.

The rule behind this (ADR-BR-035) is simple: evidence must come from tests that really ran. A document that only says "the specification requires X" proves nothing. An evidence pack points every line at the run that produced it: which test, which package version, which machine, when.

What it cannot do

Evidence about one component is not validation of your system. The companion helps you validate; it cannot do it for you.

Section 7

Promises it will never make

Over-claiming is a real danger in regulated software. A sentence like "this library is Part 11 compliant" can lead a team to skip work they still have to do. So decision ADR-BR-034 lists, as numbered items that documents and release notes can be checked against, what neither Bridger package will ever claim. Neither package claims that Bridger:

  • makes you compliant with Part 11, Annex 11 or any other rule
  • is validated or qualified
  • logs people in, or proves who an actor really is
  • stores or archives records durably
  • can prove records were not tampered with
  • makes an electronic signature legally binding
  • keeps clocks synchronised
  • checks, signs or sandboxes plugin code
  • isolates plugins from one another
  • turns its live event stream into an audit trail
  • undoes the effects of a plugin that failed
  • reviews your trail or performs your PQ
Section 8

Questions still open

The companion's specification has not been written yet. These are the questions it will have to answer. Raising them now helps the core be built in a way that leaves room for good answers.

Approvals take hours, the gate waits a minute

The core refuses a change if the gate has not answered within its time limit (60 seconds by default). A human approval can take far longer. The likely answer is the approval ticket shown above: sign first, then change. It is not settled.

Keeping a signature on its own change

A signature must not be reusable on a different change (Part 11 §11.70). The specification must say exactly how a signature is bound to the change's identifier and the plugin's digest.

Managing fingerprint keys

Where the secret key lives, how it is rotated, how older fingerprints stay comparable, and which settings are too guessable to fingerprint at all.

What the evidence pack looks like

Which fields identify a run, how each line points at a requirement, and how a new pack is compared with the previous release's pack.

Order of work

The roadmap requires the companion's specification to be approved before any companion code exists. Because the companion is built on the core's ports, the core's first phases come first: then the companion is designed against real interfaces rather than paper ones.

Section 9

Six scenarios

To see how the pieces fit, follow one plant through six situations. A tablet factory runs a Bridger host called line-3-host on its production line. Plugins on it read the analytical balance, drive a dosing pump and print labels. Its audit trail is written to the plant's Postgres database by an adapter that passes the companion's conformance tests.

People, record numbers, identifiers and digests are invented for the examples, and audit ledgers are trimmed to the columns that matter.

Ainstalled and fully recorded

An approved plugin is installed

Change request CR-2026-118 introduces lab/balance-reader version 2.3.1. The QA lead, Dr. Amal Haddad, approves it in the morning. The operator, Karim Benali, installs it during the afternoon shift.

  1. Dr. Haddad approves the exact build: install lab/balance-reader, version 2.3.1, digest sha256:7be1…. The plant's single sign-on asks her to log in again, and the companion stores her signature with the meaning "approval" as ticket APR-0419.
  2. Karim installs the plugin, giving the reason CR-2026-118 and the ticket number.
  3. The approval gate looks up APR-0419, checks that the operation, plugin, version and digest all match, and allows the change.
  4. The core records the request, registers the plugin, records the result, and then records the plugin's start, linked back to the request.

Why it matters. Years later, a reviewer can start from Dr. Haddad's signature and follow APR-0419 through records 2207 to 2209 to the moment the plugin started. The records also carry the version and digest, and they match what she approved.

Brefused, nothing changed

An unapproved build is refused

A week later the vendor sends version 2.3.2 with a "small fix". Karim tries to replace the running plugin and reuses ticket APR-0419, the one he has.

  1. The gate compares the ticket with the request. The operation, version and digest do not match.
  2. The gate refuses: "approval does not cover this definition".
  3. The core writes exactly one rejected record and no requested record. Version 2.3.1 keeps running, untouched.

Why it matters. Even the refusal is on record: who tried, what they tried, and why it was stopped. Note that the digest is a label the gate compares. Bridger does not check that the plugin's code really matches it.

Cfail closed, alarm, acknowledged

The audit database goes down at night

At 02:14 the plant's Postgres server fails over to its standby. For about seventeen minutes, writes hang longer than the core's audit time limit (10 seconds by default).

  1. An operator tries to restart the balance plugin. The core cannot record the request in time, so the restart fails with AuditUnavailable and nothing restarts. No record, no change.
  2. At the same moment, the outcome record of an earlier change cannot be written either. The core turns on the audit alarm. From now on every operator change is refused; only shutting down is still allowed.
  3. The core keeps retrying the unwritten records with the same identifiers. When the database returns at 02:31, the adapter's "store once" rule makes those retries safe.
  4. At 02:40 the QA on-call acknowledges the alarm with the reason "DEV-0077: database failover 02:14–02:31". A reason is mandatory, and acknowledging only works once records can be written again.

Why it matters. This scenario only works because the adapter told the truth. An adapter that reported success while the database was down would have kept the alarm off, and nobody would have known that records were missing.

Dgap found, deviation opened

The monthly review finds a gap

Annex 11 §9 expects audit trails to be reviewed regularly. At the monthly review, QA runs the companion's check over the stored trail of line-3-host.

gaps:        after 2,309, before 2,311   (1 record missing)

  1. Record 2310 is missing. QA opens deviation DEV-0081.
  2. The investigation finds a manual database restore on 12 September that lost one row. The records on either side, and the host's logs, narrow down what the missing record was about.
  3. The finding and the corrective action go into the plant's quality system. That step is entirely the plant's own.

Why it matters. The numbering turned a silent loss into a visible one. Its limits are clear too: it could not have spotted an edited record that kept its number, or lost records after number 2,480. Those risks belong to the database's own protections.

Ereverted, values never stored

A configuration change is reverted

Under change request CR-2026-131, process engineering widens the balance tolerance for a trial, then puts it back when the trial fails. An auditor asks: is the final value really the original one?

The fingerprints add the proof that record 2417 restored exactly the value in force before 2402, without the trail ever holding the value. Because a tolerance has few likely values, the plant must first decide whether fingerprinting this field is acceptable (part 4 above).

Fevidence produced, PQ by the plant

Requalifying after a Bridger upgrade

IT wants to upgrade @bridger/core to its next release. The plant's change procedure requires fresh IQ/OQ evidence for the component before anything reaches production.

  1. In the qualification environment the team installs the new release and runs the companion's evidence task.
  2. IQ: the package name, version and digest match the release record, and its one dependency, effect, is at the pinned version.
  3. OQ: all 54 acceptance requirements, REQ-BR-001 to 054, run against the installed package. Each result carries the run identifier, date and machine, and the pack lists what differs from the previous release's pack.
  4. Plant QA reviews the pack, then runs its own PQ on line 3 with the real balance plugin. Only then does the upgrade go live.

Why it matters. The evidence describes what actually happened. Had one requirement failed, the pack would show the failure instead of a hopeful "pass", and the plant would decide what to do before going live.
