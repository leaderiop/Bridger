02 · Patterns

Most findings trace back to four causes.

Round-6 decisions checked against one case onlyThe deadlock check tests leases on the child but not on the dependents its removal stops first (H1), and the surrounding cases (self-revoking unmount, "has begun", a draining stop outside the parent's) are still open (C1–C4). The keyring fence decision was checked against a freeze but not against SQLite's single writer or the order in which the bus resumes readers (H3, H4, K1).
Two trees each assumed the other sideFederation pinned proxy digests and assumed that admits installs; the loader gate admits only acceptances and exemptions (H2). The agent rule says a result "reaches the handle" that only the loop holds (H5). Federation re-verifies at boot without the loader's new acceptedAt form (L3) and never retries the gate's new stale refusal (F2).
The new cold option was not walked through every pathIts exclusion sentence contradicts the skip record (C6); joins and supersedes have no outcome (C7); plans and expect cannot carry it (C8); summaries, events and binding lists lag (CL5, PL17–PL18).
Propagation, as every roundThe shutdown requested exception (CL1, three reviews), step-4b order (CL4), traceability rows (CL11), the roadmap row (CL6), stale revocation-through-reconcile text in core (CL12), catalog rows (PL2, PL4, PL11).
03 · High severity

H1The round-6 deadlock check looks only at leases on the child, but the child's removal stops its dependents first gapverified

Where
core/behaviors/14-children-and-groups.md:64-70, :90-95, :514-520; 09-leases.md:457-461; invariants.md:579-581 vs 09-leases.md:586-593 (BEH-BR-088), 14:57, 08-operation-legality.md:48-50, 09:391-394
Evidence
14: the finalizer "MUST NOT wait on a lease held by the fiber that closes the sub-scope", but the trigger is "holds a lease on the child". The removal still stops "its dependents first", and revoking a scoped lease "MUST interrupt the fiber that acquired it". A closing fiber that leases a dependent D of the child passes the check, waits on D's drain, and D's revocation must interrupt the finalizer's own fiber, which cannot be interrupted: the round-6 H2 hang returns. unmount from a fiber leasing D, while the parent's operator stop parks D, waits forever. BEH-BR-088 already uses the right set: "any provider whose stopping would first stop P". Found by two reviews.
Fix
Trigger on a lease on the child or on any plugin the child's removal stops first (its dependents, transitively), in 14 (both rules), 09 BEH-BR-086, INV-BR-016/017, ADR-016/038 and check 89.

H2LoaderGate still refuses every import proxy at install/replace; pinning lifts only "verification-unknown" contradictionverified

Where
federation/behaviors/01-host-manifest.md:440-456, 04-exports-and-imports.md:105-110 vs loader/behaviors/02-load-pipeline.md:400-405, :423-434; core/behaviors/25-operation-gate.md:410
Evidence
Federation: proxy digests are published with setPinned("@bridger/federation", …) "so that no gate or link refuses an import proxy "verification-unknown"; the application passes nothing more to them." Loader: "For install and replace, the piece MUST return Refuse unless (a) lookup … returns an acceptance with current true … (b) … listed in exempt.ids, or its digest is listed in exempt.digests". A pinned digest is neither, so every proxy install and every disclosure-change replace is refused "digest-not-accepted" on any host that wires LoaderGate. Round 6's own fix text asked for "the matching gate exempt". Found by two reviews.
Fix
Let BEH-LD-015 admit install/replace of a digest in AcceptedDigests.pinned (at least under the "@bridger/federation" source), and add a check; or require the application to exempt proxies and drop "passes nothing more".

H3shred called inside a durable-bus handler deadlocks on SQLite against the handler's own transaction contradictionverified

Where
keyring/behaviors/03-shred-and-acceptance.md:84-97, check 10 (:490-493) vs 03:289-294, durable-bus/behaviors/07-core-bus-and-adapters.md:252-254
Evidence
Round 6 (K3): "shred MUST ignore a StoreTransaction in its caller's environment (a durable-bus handler's, for one)" and, on an outbox-sharing store, writes the tombstone and notice "in that one transaction" — a new KeyStore.transaction on the outbox's database. The SQLite adapter runs "every bus transaction as an immediate write transaction (single writer…)", and keyring's own reason for writing in the handler transaction is to "never wait on a second writer of the same database". The handler waits for shred, which waits for step 1's commit, which waits for the handler's write lock. A second cycle: a handler holding a fence admission makes a freeze wait on it while shred waits for the thaw.
Fix
Decide shred under an ambient handler transaction on an outbox-sharing store: commit step 1 after the handler ends (receipt returned with step 1 pending), or refuse with a stated error. Restate check 10.

H4The store-swap re-apply takes the fence, so it cannot commit before subscriptions and projections resume, and they halt on refused decrypts contradictionverified

Where
keyring/behaviors/03:111-123, :357-372, keyring/README.md:162, INV-KR-002 vs durable-bus/behaviors/06-replay-and-snapshots.md:390-401, :478-483; event-store/behaviors/05:155-158, 03:93-97; durable-bus/behaviors/03:271-275; keyring/behaviors/02:155-166
Evidence
The re-apply runs "in one KeyStore.transaction (which takes the fence first)", and decrypt is refused "from the OriginChange until the re-apply … has committed". But fence refuses while the freeze holds, the freeze holds "until the settlement's Scope closes", and the OriginChange comes before the thaw. Subscriptions resume when the scope closes and event-store projections restart right after the OriginChange; a decode failure is poison "without retry" and keyring tells subscribers to use onPoison: "halt". So the refusal always overlaps reads, against "refuse reads briefly", and the INV-KR-002 residual names the wrong window (it lasts until the thaw).
Fix
Run the re-apply inside the install, after the OriginChange and before the thaw and the resumption: a durable-bus post-switch participant step, or a fence that admits writes to the new store after the switch. Restate INV-KR-002 and RSK-KR-001.

H5Nothing lets a subagent's result "reach the handle", so the round-6 A5 race is still open gapverified

Where
agent/behaviors/04-subagents.md:302-308 vs 02-tasks.md:177-181, :260-263, 01-agent-seams.md:163-168
Evidence
04: "Settling that result and a cancel … MUST be decided by the first-to-reach-the-handle rule of BEH-AG-011: the settlement counts as reaching the handle". The handle is the loop's private cancel closure passed to TaskRegistry.register, BEH-AG-011 orders only cancels, and SpawnStart carries only parentTaskId, toolset, taint and heldByParent. Neither the subagent's loop (which publishes awaiting-approval) nor spawnSubagent (which owns the result and only watches snapshots) can take part in the handle's ordering.
Fix
Declare who settles the result and through what, e.g. SpawnStart.deferred(draftId, commands): Effect<boolean>, serialised with the cancel handle and settling only if no cancel came first; extend BEH-AG-011 to it.
