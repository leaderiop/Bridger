Short answer

Not yet. The missing part is the expert toolkit, not the checker.

Bridger's spec is a set of Markdown files held together by a 305-line shell script. SpecForge could do that job better with a typed graph, executable test proof and generated tables. Today it cannot, for three hard reasons and one big gap in the ecosystem.

Blocker 1

IDs with hyphens

The parser refuses BEH-BR-041. Every ID in Bridger has hyphens.

Blocker 2

One text block per behavior

A behavior has one contract string. Bridger has about 800 separate requirement blocks.

Blocker 3

No expert toolkit

Nobody has packaged a standard like Bridger's as a plugin yet, and authors lack the tools to do it.

Good news

The base is stronger than I first said

7 built-in extensions exist, including decisions, risks, constraints and a Vitest test collector.

In one sentenceSpecForge is a good engine with few ready-made rulebooks. Bridger needs a rulebook that does not exist yet, and someone has to write it once so every user can just install it.
Update, revision 2The goal moved from "bind Markdown to a graph" to "everything lives in .spec files and the Markdown is generated". I measured the corpus: about a fifth of it is structure and two thirds is hand-written text, so prose must be stored verbatim. The tool can already hold that text, but it cannot print documents yet. See Part 6.
Correction to earlier messagesI first tested only 2 of the extensions and said rules always need Rust. Both statements were wrong. There are 7 built-in extensions, and most rules can be written without code. This report uses the corrected facts.
Part 1

What SpecForge is, explained with a pinboard

Picture a detective's pinboard. Each pinned card is one fact: a requirement, a rule the system must obey, a decision. Strings connect related cards. A good board lets you ask: "what hangs off this card?" and "which cards have no string at all?"

SpecForge builds that pinboard from text files. You write cards in .spec files. A compiler reads them, connects the strings, and tells you what is broken or unproven.

The extensions that exist today

ExtensionCard types it addsThink of it as
productfeature, journey, milestone, module, release, persona, term …the planning vocabulary
softwarebehavior, invariant, event, type, portthe engineering vocabulary
governancedecision, constraint, failure_modedecision records, quality targets, risks
formalproperty, axiom, protocol, refinement, processmathematical-style checks
testing(none, adds verify meaning)"this claim is proven by a test"
vitest, cargo-test(none)readers that link test results to cards
Why this mattersAn extension is like an expansion pack for a board game. The base game is empty. The expansion brings the pieces and the rules.
Part 2

What the Bridger spec actually holds

The folder references/core is a spec for @bridger/core, a library that lets an application add and remove plugins while it runs. The spec is Markdown, but it behaves like a pinboard already. Every file has numbered cards, and every card links to others.

ItemRough count
Behaviors (BEH)222
Invariants (INV)30
Decisions (ADR)40
Risks (RSK)about 24
User requirements (URS)about 28
Requirement blocksabout 800

Counts come from searching headings and block labels, so they may be off by a few.

Under every behavior sits a small block of links: Satisfies, See, Invariant, Risk, Regulatory. Together there are roughly 700 of them.

Example: how one behavior looks in Markdown today

## BEH-BR-041: remove stops a plugin and unregisters it after cleanup

> **See:** ADR-BR-006
> **Satisfies:** URS-BR-002
> **Risk:** RSK-BR-004

REQUIREMENT: `remove` MUST stop the plugin ... and MUST unregister
             its definition only after its cleanup has completed.

REQUIREMENT: `remove` MUST complete only once the plugin has no
             snapshot entry ... a `plugin-removed` event MUST be emitted.

Notice what the text carries: an ID, three kinds of links, and several separate rules. A tool that wants to replace this must hold all three.

What the shell script checks

GroupChecks

Part 3

What I tested, and what happened

I copied nothing into your repo. All experiments ran in a scratch folder with the installed specforge 0.1.0, then I confirmed the results against the SpecForge source code at ~/Projects/Perso/SpecForge.

Experiment 1: use a Bridger ID

behavior BEH-BR-041 {
  contract "remove stops a plugin"
}

[E001] Error: syntax error: unexpected '-BR-041'

The grammar defines an identifier as letters, digits and underscores. The source confirms it: /[a-zA-Z_][a-zA-Z0-9_]*/. A hyphen ends the name.

Experiment 2: use underscores and Bridger's link fields

behavior BEH_BR_041 {
  contract "..."
  invariants [INV_BR_017, INV_BR_999]     // does not exist
  satisfies  [URS_BR_002]               // Bridger's link
}

[E003] unresolved reference 'INV_BR_999'      // good: dangling links are caught
[W020] unrecognized field 'satisfies'            // no place for Bridger's links

How each Bridger item fits the built-in card types

Findings from the source code

  • Extensions can declare card types, fields and links in a plain manifest.json. No Rust needed for that part.
  • Rules also have a declarative form with six check types: no_incoming_edges, no_outgoing_edges, missing_field_when_flag_set, field_value_constraint, cycle_detection, file_exists.
  • A seventh check type, custom, runs your own code compiled to WASM.
  • The vitest extension links a passing test to a card through meta: { specforge: { behavior, verify } }.
  • There is no public registry yet. Extensions come built in or from a local path.
Part 4

The real purpose: experts write the rules, users just use them

You made a point that changes the design. SpecForge exists so that an expert, say a GxP validation specialist, packages hard-won knowledge once. Everyone else installs it and writes content. Users should not invent their own standard.

What the user's side looks like

// specforge.json (the only configuration the user touches)
{
  "extensions": {
    "@acme/gxp": {
      "profile": "strict",
      "settings": { "idInfix": "BR", "package": "bridger-core" }
    }
  }
}

If a rule must be bypassed, the user files a waiver: a rule code, a card, a written reason and an optional end date. A waiver is visible in reports, so an exception can be audited instead of silently weakening the standard.

What experts are missing today

#Missing pieceWhy an expert needs it
E1A richer declarative languageSix check types cannot express counts, ranges, computed values or reports.
E2A non-Rust way to authorDomain experts are not Rust developers. The scaffold needs a Rust toolchain and a WASM target.
E3A test harness for a standard"This bad spec must produce exactly these errors", run in CI.
E4A user-facing configuration contractTyped settings, named profiles and waivers.
E5Packaging of templates and docsAn expert should ship starter files and generated reports with the rules.
E6Registry, signing, versionsNo public registry, so sharing an expert's work is not possible.
E7The actual standardsNo GxP, URS/REQ or regulatory-mapping extension exists.
E8Core hooksID characters, requirement statements and Markdown binding must be exposed by the core.
The readiness testCan an expert package everything in references/core/process/ plus the shell script as one extension, so Bridger holds only content and a profile? Today the answer is no.
Part 5

Four designs that close the gaps

These are proposals, not features that exist. Each shows only the interface a person would use, not how to build it.

Design 1: IDs with hyphens

Allow hyphens inside identifiers, but only when the project opts in, and let each card type declare a pattern its IDs must match.

// project setting (opt-in)
{ "identifiers": { "charset": "kebab" } }

// card type declared by the extension
{ "keyword": "behavior", "idPattern": "BEH-[A-Z]{2}-\\d{3}" }

// what the user writes
behavior BEH-BR-041 "remove stops a plugin" {
  satisfies [URS-BR-002]
  invariants [INV-BR-017]
}

Design 2: several requirement blocks per behavior

Today a behavior has one text field. Bridger needs many separate rules per behavior, each with its own link to a test. The core already has a precedent: verify is a reserved line inside a card, and the testing extension gives it meaning. I propose the same pattern for requirement.

behavior BEH-BR-041 "remove stops a plugin" {
  satisfies [URS-BR-002]

  requirement r1 MUST """
    `remove` MUST stop the plugin through the stop path,
    and MUST unregister its definition only after cleanup.
  """
  requirement r2 MUST   "The plugin MUST have no snapshot entry on success."
  requirement r3 SHOULD "Dependents SHOULD end waiting with missingServiceIds."

  verify unit "r1: unregister happens after cleanup"
}

// the extension declares the statement once (expert side)
"statements": [{
  "keyword": "requirement",
  "args": [ {"name":"id","type":"local_id"},
            {"name":"level","type":"enum","values":["MUST","MUST_NOT","SHOULD","SHOULD_NOT","MAY"]},
            {"name":"text","type":"string"} ],
  "addressable": true, "min": 1
}]
Plain versionA requirement becomes its own small card inside a behavior, with an address like BEH-BR-041.r1. Tests and links can point at it, and a missing test shows up as a gap.

Design 3: cross-cutting rules, written by the expert

These rules sit inside the extension, never in the user's files. Each has a code, a message and a fix hint, just like the built-in checks.

rule status_honesty {
  severity error
  when    spec.implementation == "absent"
  forbid  decision where status in ["Accepted"]
  message "{kind} {id} cannot be {status} while implementation is absent"
}

rule risk_has_control {
  severity error
  require failure_mode has >= 1 edge [controlled_by]
}

rule ids_contiguous {
  severity warning
  contiguous behavior by number(id) per package
}

rule restricted_claims {
  severity error
  forbid_terms ["validated", "qualified", "compliant"]
     in [requirement.text]  unless_nearby ["not", "consumer", "companion"]
     allow "claims-allowlist.spec"        // stale entries fail too
}
VocabularyMeaning
require / forbidsomething must (not) be true of a matching card
has >=, <=, == Ncount links or statements
unique · contiguous · withinIDs and ranges
when …apply only if a condition holds
forbid_terms … unless_nearbyword lists with exceptions and an allow-list

Design 4 (revised): the spec is the source, the Markdown is generated

My first version kept prose in Markdown and bound it to the graph. You asked for more: convert everything, ADRs included, into graph and .spec files, and generate Markdown that looks exactly like references/. That is a bigger design, and Part 6 covers it with measurements. In short: prose moves into the spec as verbatim text fields, and a layout shipped by the expert extension turns the spec into the document set.

SupersededThe heading-binding and sync --check idea is dropped. Generated links cannot point at a missing heading, so there is nothing left to check.
Part 6

Going all the way: the spec is the source, Markdown is generated

The goal: every document in references/ comes out of .spec files, byte for byte, and people only edit the spec. Before designing it, I measured what the files are made of. A second pass read the SpecForge source for what it can already render.

5. An ADR, converted

Every ADR has the same five sections, so ADRs convert cleanly. The picture shows where each part of decisions/015-leases-one-primitive.md goes.

decision ADR-BR-015 "Leases are one bounded primitive with a supervised child" {
  revision 0.3
  status   Proposed
  history  change { rev 0.3  date 2026-10-03  ccr CCR-BR-013
                    text "Scoped-lease revocation interrupts the acquiring fiber" }

  context md """
    A caller that obtains a plugin's service and then calls it must not
    have the provider's scope closed in the middle of the call ...
  """

  point "One primitive."   md """`lease(keys, { realm })` is the primitive ..."""
  point "Canonical order." md """Multi-key leases are acquired in a canonical key order ..."""

  alternative "Reference counting on the caller's fiber, no child."
              rejected md """Force would have to interrupt the caller's own fiber ..."""

  positive md """No provider closes under an admitted call unless ..."""
  negative md """..."""
  tradeoff md  """..."""

  behaviors  [BEH-BR-081, BEH-BR-082]       // real edges, rendered as links
  invariants [INV-BR-017]
  risks      [RSK-BR-001]
  source md """SPEC.md "Leases" ..."""
}

Cross-links inside prose are written as {ref INV-BR-006} and rendered to the relative link plus anchor. Of 3,129 links in the corpus, about 85% sit in structured places (link blocks, tables, reference lists). Only about 360 are in free prose. Anchors follow GitHub's heading-slug rule, and risks use an explicit <a id>, so both can be produced exactly.

What does not fit neatlyAbout 12 one-off bullets under References (for example "Ordering rule") are really bold-lead-in prose, so the spec needs a free note "label" md """…""" statement. Four ADRs also carry small tables, which stay inside the verbatim text.

8. How to prove it before changing the core

A golden round trip needs no core change. An outside script does the printing, so the experiment shows exactly which features cost how many files.

9. What changes if you go this way

  • Checks that disappear by construction: index equals disk, link and anchor resolution, the derivable trace tables, the Document Control shape. That covers check 1, check 12 and parts of checks 2, 3, 5 and 8.
  • Authoring cost: people write prose inside """ in .spec files, with no Markdown preview. This is the main usability risk, and an editor or preview command should be part of the plan.
  • Review: commit the generated Markdown and gate it in CI, so reviewers still read Markdown and nobody edits it by hand.
  • Exactness: byte-identical output is plausible for all 80 core files if prose is stored verbatim. That is an expectation until the round trip is run.
Part 7

Why not put every rule in a WASM plugin?

WASM is already the escape hatch in SpecForge, and it is the right home for some rules. It is a poor default for most of them.

ConcernDeclarative ruleWASM plugin
Who can write itAnyone who writes specsNeeds Rust, a WASM target, an SDK, a build
Review in a pull requestReadable text diffSource plus a binary
Free toolingExplain, editor hints, rule listsEach rule builds its own messages
Host understands itYes, so it can rebuild only what changedNo, it only sees pass or fail
SecurityNo code runsThird-party code runs during check
Data it seesThe whole graphOne card and its direct links (per-card API)
Expressive powerClosed vocabularyAnything
Plain versionWriting a Rust crate to say "every risk needs a control" is like hiring a locksmith to close a door. Keep WASM for the two or three rules that need real programming, such as the restricted-words check.
Part 8

One shared language for rules and more

You asked why a declarative language should serve only rules. It should not. If the language is a small query and condition core, many extension features can reuse it. This lets an expert ship far more without writing code.

Three examples an expert could ship

// 1. computed value, replaces a documented gap: RPN is never checked today
derive failure_mode.rpn = severity * occurrence * detection

// 2. a view that renders traceability.md, so it can never go stale
view behavior_to_risk {
  from behavior b  join b -[risk]-> failure_mode r
  select b.id, r.id, r.severity   order by r.severity desc
}

// 3. an executable definition of done
gate release_ready {
  require count(failure_mode where severity >= "high" and not has edge [mitigated_by]) == 0
  require proof_pct(behavior) >= 0.9
}
Guard railsKeep the language closed: no loops, no recursion, no file access, and it only reads the graph. Check every field name against the loaded schema so a typo is an error, not an empty result. Version the language so older tools can refuse new syntax cleanly.
Part 9

Recommendation and next steps

Now

Keep Markdown as the source

It carries the prose, anchors and reviewed reasoning. The shell script already enforces your domain rules.

Optional trial

Generate a read-only projection

A small script turns headings and link blocks into .spec files so you can try graph queries. It is throwaway. Hyphen IDs must be mapped to underscores for now.

Core changes

Four for SpecForge itself

Hyphenated IDs (Design 1), ordered statements (Design 2), a verbatim md field with source order kept, and a document renderer with a drift check (Part 6).

Ecosystem

Then the expert toolkit

Expression core, test harness for standards, typed settings and waivers, and a registry. Then package Bridger's standard as one extension.

Open questions

  • First proof. Run the ADR round trip with an outside script before any core change? It shows how many of the 39 ADRs come out byte-identical and which feature costs how many files.
  • Authoring. Prose now lives in """ blocks. Is an editor extension or a live preview a requirement before migrating?
  • Waivers. Keep them, with a mandatory reason and an end date? They make strict standards usable, but they let users loosen a standard.
  • Kebab IDs. Reject a hyphen where it could be confused with a negative number? The grammar has no arithmetic today, so I think it is safe.
  • Requirement IDs. Require a hand-written local ID (r1) or auto-number? I prefer hand-written, so inserting one does not renumber the others.

What I did not verify

  • Whether the corpus round-trips byte for byte. The renderer pass confirmed there is no Markdown export of entities, but no migration or render script was run.
  • The WASM validator interface beyond reading its description file. No custom WASM extension was built or run.
  • How rules in product behave on real data. I only confirmed it installs.
  • Whether the Vitest collector works with Bridger's actual tests. No test run was attempted.
  • All counts of Bridger items are approximate.
Glossary

Words used in this report

spec
A written description of what a system must do, in a form a tool can read.
card / entity
One item on the pinboard: a behavior, a decision, a risk.
string / edge
A typed link between two cards, such as "satisfies" or "proved by".
graph
All cards and strings together. You can ask it questions.
extension
A plugin that adds card types, links and rules to SpecForge.
manifest
The plain file that describes an extension to SpecForge.
declarative rule
A rule written as a statement ("every risk needs a control"), not as program code.
WASM
A compact format that lets an extension ship real program code to run safely inside the tool.
invariant
Something that must always be true while the system runs.
ADR
Architecture Decision Record: a written decision with its reasons and alternatives.
MUST / SHOULD
Words that say how strong a requirement is (a standard called RFC 2119).
traceability
Being able to follow a requirement through to the code and the test that proves it.
GxP
Quality rules for regulated industries such as pharma, where records must be provable.
waiver
A recorded, reasoned exception to one rule.
projection
A generated copy of the data in another format, used for experiments.
verbatim
Stored exactly as written, with line breaks kept, and never reformatted.
round trip
Convert A to B and back, then compare with A. An empty difference proves nothing was lost.
layout / template
A fixed shape for one kind of document, filled in from the spec data.
registry
An online catalog where experts publish extensions and users install them.
