A sixth semantic pass over all 15 spec trees and the user guides, run on 7a0b81f (the round-5 fixes, CCR-BR-037 and companion CCRs). The mechanical verifiers pass; everything here is a problem of meaning.

02 · Patterns

Most findings trace back to four causes.

D1's own rule does not holdThe WouldDeadlock refusal fires only once the child's stop is already parked, so a wait entered earlier can hang (H1). Revoking the closing fiber's own lease interrupts a fiber running an uninterruptible finalizer (H2). A finalizer cannot fail, so the error has nowhere to go (C1). Remote still promises a removal the sub-scope close no longer does (R1). The new raisers reached neither the ADRs nor the catalogs (C3).
Obligations with no mechanismThe adapter must end fence admissions but has no hook to do it (H3). heldByParent must answer from a pending draft that spawnSubagent cannot see (H10). The publisher binding must be re-checked from a record that lacks it (H5). Import proxies need pinning nobody passes (H9). The gate needs a maxAge it does not take (L4); ReconcileResult is undeclared.
Federation delivery importsRound 5's delivery-only state and dependent check opened new holes: a bus that depends on the import deadlocks with federation (H7), a manifest-installed dependent blocks every retry for good (H8), a new ResyncRequired resets installAttempted (F2), and links that drop while suspended still have no rule (F3).
Round-5 fixes not carried throughSmaller, as in every round: the latch and CloseTail rules for unnumbered records (C2), { id, realm } records for parents, children and several restatements (C5, CL5–CL7), INV-GX-009's new exceptions against "never weakened" text (PL1–PL2), the agent checks behind the hand-off exception (A4), and the keyring invariant behind its new crash window (K2).
03 · High severity

H1A sub-scope close only refuses with WouldDeadlock when the child's stop is already parked, so a wait that starts first can hang forever gapverified

Where
core/behaviors/14-children-and-groups.md:96-104, :241-244, 09-leases.md:446-457, invariants.md:670-675 (INV-BR-017) vs decisions/038:65, 02-host-construction.md:386
Evidence
14: "When the child's stop is parked with an operator call at the root of the parent's stop while the fiber that closes the sub-scope … itself holds a lease on the child … the finalizer MUST then fail with WouldDeadlock". ADR-038 says the refusal is "decided before any wait", and INV-BR-017 says such a wait is "refused instead of entered". If the sub-scope closes while the parent's operator-rooted stop is still draining, the stop is not yet parked, so the finalizer enters the wait; when the drain then expires unforced and parks, no rule ends the wait, which can never end because the closing fiber holds the lease. A drainTimeout of "forever" never parks at all. Found by two reviews.
Fix
Decide at the start of the wait from "operator-rooted parent stop in progress + lease in the caller's HeldPlugins", or fail the waiting finalizer at the moment the stop parks. Say what "forever" does here.

H2A sub-scope finalizer that revokes the closing fiber's own lease cannot finish, because revoking interrupts that fiber contradictionverified

Where
core/behaviors/14-children-and-groups.md:64-74, :89-95 vs 09-leases.md:384-394
Evidence
14: a lease on the child "held by the fiber that closes the sub-scope, or by a fiber it awaits, MUST NOT make the finalizer fail with WouldDeadlock there — the drain runs under drainTimeout and revokes that lease at the limit". 09: revoking a scoped lease "MUST interrupt the fiber that acquired it", and revocation waits for its finalizers. The fiber is running an uninterruptible scope finalizer, so the interrupt never takes effect and the removal never settles. The same holds under shutdown and on no-caller paths. If the wait were made interruptible instead, the sub-scope would close with its child still registered, against 14:64-66.
Fix
Refuse with WouldDeadlock for every sub-scope close whose closing fiber (or a fiber it awaits) holds a lease on the child, or define a revocation that does not interrupt or await the closing fiber.

H3No port lets the storage adapter end a fence admission at commit or rollback gapverified

Where
durable-bus/behaviors/07-core-bus-and-adapters.md:232-236, 06-replay-and-snapshots.md:455-459 vs 02-transactional-outbox.md:37, :174-175; event-store/behaviors/05:86-93; keyring/behaviors/01:112-114; 08-testing-and-acceptance.md:36-37
Evidence
Property 8: "The adapter ends every DurableBus.fence admission taken on a transaction when that transaction has committed or rolled back, on every exit". But the admission is held by the bus, and the only shared object is StoreTransaction, whose shape is { readonly handle: unknown }. The bus reaches storage only through OutboxStore/InboxStore, and neither has a commit or rollback hook. The same obligation was copied to event-store, the KeyStore and TestStore, with no hook in any of them.
Fix
Add a hook such as StoreTransaction.onEnd(finalizer) (or an ended Deferred), which the adapter runs after commit or rollback; fence registers the end of its admission through it. Restate property 8 and the copies against it.

H4A tombstone written after the keyring's store-swap prepare is lost in the swap gap

Where
keyring/behaviors/03-shred-and-acceptance.md:84-96, :324-347 vs durable-bus/behaviors/06-replay-and-snapshots.md:393-398, :431-434; keyring/invariants.md:44-49 (INV-KR-002)
Evidence
The one-transaction retry of shred writes the tombstone alone, possibly during a whole-store freeze. KeyStore writes never call the fence, so they are not refused by the freeze. The <id>/store-swap participant re-applies only the tombstones it read in prepare. A tombstone committed between prepare and the swap is therefore dropped, and the subject decrypts again after the swap, against INV-KR-002 ("a shredded subject never decrypts again").
Fix
Make outbox-sharing KeyStore writes take the fence (with a defined outcome on OutboxFrozen), or have the participant record shreds from prepare until its re-apply commits.

H5The publisher-binding re-check after a signer revocation cannot be done from the verification record contradictionverified

Where
loader/behaviors/07-signed-statements.md:499-501 vs 03-signature-policy.md:109-114, :264-274; 04-revocation-and-kill-switch.md:521-531 (BEH-LD-030)
Evidence
07: "A re-evaluation after a signer revocation (BEH-LD-052) re-checks the binding: a package whose only matching signer is revoked fails it." RecordedSigner carries roles and inWindow "so that the record alone suffices", but not which publishers each signer may use. BEH-LD-030's re-evaluation ignores the binding.
Fix
Record per signer whether it matches the package's publisher (for example matchesPublisher) and re-check it in every re-evaluation, or delete the sentence in 07.

H6The revocation reconcile rebuilds entries from the last reconcile action, so it undoes an operator's direct changes made since contradictionverified

Where
loader/behaviors/04-revocation-and-kill-switch.md:447-461, INV-LD-005 vs core/behaviors/18-reconciliation-and-confluence.md:325-330, :360
Evidence
Loader: every installed entry is passed "as its last completed reconcile action left it (definition, override, disabled), kept by the kill switch from each ReconcileResult", so that "the diff replaces or reconfigures nothing". If an operator has since called replace, reconfigure, enable or disable directly on a plugin the scope owns, core's diff moves it back to the reconcile's version, under the revocation actor. That breaks INV-LD-005 ("its only actions are the prune removals").
Fix
Build the kept entries from the current state in Host.snapshot, or drop the reconcile and remove the dropped entries with Host.remove under the revocation actor.

H7If the bus depends on a delivery import, the federation plugin can never start, and a suspension takes the outbox port away mid-settlement gap

Where
federation/behaviors/02-sync-offline-and-rebootstrap.md:52, :97-100, :485-489, :511-522 vs durable-bus/behaviors/07-core-bus-and-adapters.md:91-94, 06-replay-and-snapshots.md:331-332
Evidence
Federation "requires Bridger.Host and the ports named in its options", including outbox, which rebootstrapOutbox(...) builds from DurableBus. The new rule allows exactly one dependent of a delivery import: "the event delivery companion's plugin, whose outbox relay it carries". If that dependency is a hard requires, the bus waits on an import that only federation's boot apply installs, and federation waits on the bus. And at step 2 ("dependents wait"), the bus goes waiting, its outbox port goes with it, and federation loses the settlement it holds.
Fix
Let the relay reach the delivery import without a hard requires (optional/whenAvailable, or a lookup per send), resolve outbox lazily at step 1, and say which kinds of use count as "depends on".

H8A dependent of a delivery import that the manifest installs blocks every re-bootstrap retry for good, and the build check cannot see it gap

Where
federation/behaviors/02-sync-offline-and-rebootstrap.md:120-125, :519-527 vs 06-kill-path-placement-and-skew.md:201-212, 01-host-manifest.md:55-60
Evidence
The "other-dependent" check reads "the host's plugin set" at build, before federation's own boot apply has installed anything the manifest declares. Step 1 then fails RebootstrapBlocked "delivery-import-dependents", even under "pushed-or-kept". While the marker is stored only kill-only applies run ("MUST NOT apply any other change"), so the manifest cannot remove the dependent, and an operator remove is undone by the next re-apply. Links stay suspended over half-replaced state, and the catalog's remedy ("remove the other dependent") cannot be applied.
Fix
Refuse such dependents in the projection (BEH-FD-005) or at every apply, or let step 1 skip the delivery-only opening and settle by "kept" when a dependent exists.

H9Every import proxy is dropped and refused as soon as a revocation set revokes any signer gap

Where
federation/behaviors/01-host-manifest.md:425-431, 04-exports-and-imports.md:105-108 vs loader/behaviors/04-revocation-and-kill-switch.md:351-356, 09-trust-class-and-guest-links.md:495, remote/behaviors/02-sessions-and-epochs.md:296
Evidence
Proxies carry a synthetic meta.digest "derived deterministically from (from, K, V, …)", so they have no AcceptedDigests record. Federation passes every desired list through filterDesired, which "MUST drop the entry with reason "verification-unknown", unless the digest is in pinned" whenever the set revokes a signer, and the view answers "verification-unknown" for a digest with no record, which every remote link refuses. Federation never says what verification or pinned it passes (coordinator check: no pinned or verification-unknown in federation). One routine signer revocation therefore removes every import on every host.
Fix
Have federation pass its synthesized proxy digests in pinned (and the matching gate exempt and view pinned), or keep its proxy entries out of filterDesired. State it in BEH-FD-007 and BEH-FD-042.

H10Neither heldByParent nor the hand-off marker can be computed from what spawnSubagent receives gapverified

Where
agent/behaviors/04-subagents.md:47-51, :114-121, :149-151; 02-tasks.md:604-619; 01-agent-seams.md:166-167
Evidence
heldByParent "MUST answer for a draftId exactly as this behaviour decides the hand-off marker: true while that draft is the parent task's pending draft", and the pending draft changes "from the moment the first of the current turn's subagent results settles … whether or not the loop has yet read the result". But spawnSubagent's parent is only { taskId, sessionId, toolset, context }, Tasks shows only published snapshots, and AgentLoop is replaceable, so no private channel to the loop can be assumed.
Fix
Add an input the parent's loop supplies to request.parent (for example pendingDraft: Effect<Option<string>>), which every AgentLoop provider must offer, and derive the marker and heldByParent from it.
