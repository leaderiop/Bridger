Bridger improvement report 02 · spatial composability

Dependency model and seams

Bridger's spatial model is stricter and more explicit than Cordis: cycles are refused at install, provider slots are exclusive per realm, and contract keys carry a version and method list. Interface drift is only partly covered. Drift detection is name-only, so a changed signature under an unchanged name binds silently, and plain keys have no check at all. There is no broker seam, so replacing a provider always restarts its dependents. Interception reaches captures but not Host.use or lease. The prototype also diverges from the spec in realm-family option fingerprinting.

Recommendations

R1

Compare method schemas, not just names

HD-01

Rationale

BEH-BR-228 clause 3 only checks that every method name appears in the provision. Contracts already hold MethodSpec codecs and BEH-BR-230 states add-only evolution, but nothing enforces it. In a GxP product (RSK-BR-010, RSK-BR-025) a silent payload change is the failure the contract layer exists to stop.

Change (as built)

ContractDescriptor.schemas lists a stable per-method digest: a sha-256 of the sorted-key JSON Schema of payload, success, error and the stream flag, ignoring title, description and examples. MethodSpec.digest overrides it for a codec with no canonical JSON Schema, and a method without a digest is skipped. BEH-BR-228 clause 3b: a method both sides name must have equal digests in every compatible pair; an add-only evolution never changes a method the older side knows, so no "unless higher" exception is needed. IncompatibleContract.mismatchedMethods names the methods, and a registry add accepts a Contract.at provision so its copy is compared too. BEH-BR-231's "core never compares schemas" now limits core to opaque digests; classification stays in the kit. There is no SchemaFingerprinter port: the default is always on.

Cost / risk

Medium. Canonical JSON Schema of arbitrary codecs is hard (transformations, brands). Start with descriptor-level opt-in. Harmless refactors can false-positive; add-only classification mitigates.

Verification (as built)

r1-schema-digest.test.ts: identical copies bind (annotations ignored); a changed payload is refused from both install orders naming post; a flipped stream flag changes the digest; an add-only higher provision binds and one that edits a method does not; explicit digest and skipped methods; registry with a Contract.at provision. Mutation check: with clause 3b disabled, 3 tests fail. Kit acceptance check 30.

R2

Plain keys across package boundaries fail conformance

HD-02

Rationale

ADR-BR-011 admits drift under an unchanged ServiceId passes. ADR-BR-040 added contracts but left plain keys fully legal, so the weak path is the easy path.

Change (as built)

Core only decodes a new internal flag on a plain-key manifest reference (BEH-BR-241; refused on a contract key). The loader refuses a manifest naming a plain key not marked internal with PackageRefused predicate "plain-cross-boundary-key" (loader BEH-LD-014), and bridger check fails it with PlainCrossBoundaryKey (kit BEH-KT-028, error catalog entry). ADR-BR-011 records that the weak path is now explicit.

Cost / risk

Low. Some friction for first-party internal keys; the internal annotation absorbs it.

Verification (as built)

r2-internal-key.test.ts covers the decode rules. The loader and kit rules are specification only: no loader or kit prototype exists, so they are covered by kit acceptance check 30 (REQ-KT-030, not run).

R3

A broker seam for provider swaps

MD-03, D-12

Rationale

ADR-BR-003 rightly refuses multiple providers per key, but a replace currently stops all dependents. For a long-running ERP host that is a large blast radius for a patch. Registries multiplex by id; they do not give "one service, many implementations behind it". D-12: no porting recipe exists for Cordis accessor/mixin patterns.

Change (as built)

Broker.make(contract, {name, range, select, drainTimeout}) (BEH-BR-168, src/broker.ts) makes a contract registry and a facade with one function member per contract method. Each call chooses a contribution ("first" = lowest priority number, a function, or Broker.byKey), runs the member under a lease, and reselects once if the choice was withdrawn meanwhile; no contribution gives ContributionUnavailable. The chosen id reaches the call log through CurrentCall.contributed, recorded as CallEntry.contribution. The Cordis porting recipe is a paragraph of BEH-BR-168. The selector names differ from the proposal (first, function, byKey; by-priority equals first because the view order is priority order). Limit stated as Open: a stream method is leased while it is produced, not consumed.

Cost / risk

Medium; additive, built on existing primitives. Risk: the broker hides provider identity from audit, so CallLog (BEH-BR-029) must record the chosen contribution id.

Verification (as built)

r3-broker.test.ts: delegation, selection by key, typed failure when empty; a swap under an in-flight call (old drains, new calls reach the new one, no plugin restarts); contract-mismatched contribution refused at add; the call log carries the contribution.

R4

Make interception limits unmistakable and inspectable

MD-04, D-09

Rationale

BEH-BR-151 deliberately wraps at capture only, and BEH-BR-152 notes authorization or rate-limit wrappers must not be called a boundary. Cordis's intercept is also not security. The risk is documentation plus invisibility: inspect shows no interceptions.

Change (as built)

As proposed. BEH-BR-151 states that restriction belongs to mandatory interception (BEH-BR-262). Interception and MandatoryInterception take an optional id; PluginInspection.interceptions lists {key, source, id?} in composition order: realm, inherited, install, then mandatory (own chain, realm, host). Ids only.

Cost / risk

Low. Needs an optional id on Interception.

Verification (as built)

realms.test.ts (report 02 R4): parent, inheriting child, child with its own, and a plugin with none.

R5

Fix realm-family option fingerprinting

MD-05, D-06

Rationale

BEH-BR-330 requires identical isolated keys and the same interceptor objects in order. realms.ts computes {isolate ids, interceptors.length, mandatory.length}. This is the one prototype/spec divergence the review found. D-06: spec refuses empty, "/" and "bridger:" prefix; prototype accepts only [A-Za-z0-9._-]{1,64}, so keys like "a:b" differ in behaviour.

Change (as built)

Already in the prototype (sameOptions compares interceptor and mandatory objects with Object.is, and the key grammar follows BEH-BR-330, so tenant:1 is valid); the three repro tests pass and BEH-BR-330 states both rules. No WeakMap was needed.

Cost / risk

Low.

Verification (as built)

divergence-repro.test.ts (interceptor swap of the same count, key tenant:1, a dormant member).

R6

Guard the default-realm leak

MD-08

Rationale

BEH-BR-146 lets a non-isolated key provided inside a realm land in the default slot. That suits shared services but is the classic tenant-leak mistake: tenant B's install fails with DuplicateProvider (best case), or tenant A's data service is visible to everyone (worst case, when only one tenant exists at first).

Change (as built)

As proposed. RealmOptions.provideNonIsolated: "allow" | "refuse" (BEH-BR-146); "refuse" fails the install with InvalidDefinition "non-isolated-provide-in-realm". Realm families define every member with "refuse" (BEH-BR-330), so a leaking member is "rejected". The snapshot does not show the policy.

Cost / risk

Low; opt-in.

Verification (as built)

realms.test.ts (refusal, isolated key allowed, default "allow" unchanged) and r2-family-leak.test.ts (family rejects, isolated key accepted).

Minor proposals from the findings table

X1

Subscribe instead of polling in awaitActive

MD-07

Rationale

Works under TestClock; in production it is a busy poll of the full host snapshot per member creation. Judged from the prototype only.

Change (as built)

awaitActive waits on Host.changes (a snapshot subscription) bounded by the activation timeout, with no polling; BEH-BR-331 says so.

Cost / risk

Not specified in the report.

Verification (as built)

The existing family and ephemeral tests, now on the subscription (TestClock-compatible).

X2

One error channel for registry range checks

LD-10

Rationale

within(range) throws synchronously (checkRange) rather than defecting in Effect; make uses Effect.die.

Change (as built)

registry.within(range) returns an Effect that dies with the same defect make uses for a bad range or a registry without a contract; BEH-BR-233 states it. One channel, the defect channel, by spec.

Cost / risk

Not specified in the report.

Verification (as built)

p7-contracts.test.ts asserts the failure in the Effect channel.

X3

Document "tolerate temporary loss" as a non-goal

LD-11

Rationale

requires keys are undeclared for optional, so a plugin cannot treat a required key as soft after startup. The report calls this fine, but unspecified.

Change (as built)

ADR-BR-022 (revision 0.2) states the non-goal: requires is strict at install and after; a plugin that tolerates loss uses optional, and one that needs continuity across provider swaps uses a broker.

Cost / risk

Not specified in the report (documentation only).

Verification (as built)

Documentation only; verify-traceability.sh passes.

How the mechanisms work

Each animation can be played, paused, stepped and replayed. The page loads on the final step, so every figure is complete without motion. Diagrams are simplified sketches of the behaviour the report describes.

A. Contract drift: undetected today, caught by a schema digest

  1. Provider ships post v1.3 with a narrowed payload; the method name is unchanged.
  2. The compatibility check runs: today it reads names, proposed it reads schema digests.
  3. Today the names are equal and the check passes. With digests the values differ.
  4. Today the dependent binds and the drift surfaces later. Proposed, the pair is refused with mismatchedMethods before any call.

B. Provider swap with and without a lease-aware broker facade

  1. The operator swaps the provider. Without a facade the key has one provider; with one, a new implementation is added to the registry.
  2. Today the consumer, a dependent, is stopped. Proposed, the facade routes new calls to v2 while v1's in-flight calls drain under their lease.
  3. Today v2 starts. Proposed, v1 is removed once drained; a call with no live implementation would fail with ContributionUnavailable.
  4. Today the consumer restarts: the whole blast radius of a patch. Proposed, it never restarted.

C. One key, two consumers: realm and interception resolution

  1. Key K is provided in realm R1 (isolated) and in the default realm, giving two separate slots. Realm resolution is applied to the resolved graph.
  2. Consumer A in R1 resolves K to the R1 slot.
  3. Consumer B in the default realm resolves the same K to the default slot.
  4. An ordinary interceptor wraps A's capture. A Host.use call is not intercepted (BEH-BR-151).
  5. Only mandatory interception (BEH-BR-262) covers both paths, so restriction belongs there (R4).
