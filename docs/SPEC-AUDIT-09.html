02 · Patterns

Most findings trace back to four causes.

A new gate added without walking its callerswhenReadable was placed on every event-store read without checking who reads: a store-swap prepare (H4), follower batches inside a write transaction (H5), and streams already in flight (H6).
The child-stop rule grew a wait on buildsWaiting for a build in a finalizer meets the slot (H1), the end point of "settled" (C2), the parent's cascade (C1), waiting operator calls (C3), the handoff steps (C10), and the new failed(cleanup) outcome reaching realms, re-mounts and later removals (C4, C5, C11).
Fail-safe rules checked against the fail case onlyF1's "keep what runs" skips the stale disable (H2); the spawn tool skips the taint floor (A1) and the replay model (H3); L3's catalog exemption leaves acceptances current forever (L1).
Propagation, as every round23's unmount-requested rule (C9), remote checks and risks (F3), ADR-008, ADR-021, ADR-FD-007, roadmap rows, traceability and risk rows, catalog rows (CL1–CL9, PL3–PL18).
03 · High severity

H1A take-over in a finalizer waits for a build that needs the slot held by the parent build stuck in that finalizer: deadlock, and slot time is outside the stated bound gapverified

Where
core/behaviors/14-children-and-groups.md:186-190; INV-BR-017 (invariants.md:715-720) vs 05-activation.md:151 (BEH-BR-040), INV-BR-030, 14:358-360, 14:505-507
Evidence
14: the take-over waits "for that build under buildTimeout … bounded by drainTimeout + buildTimeout". 05: "A build MUST begin only once it holds a slot." INV-BR-030: builds wait for no other plugin's transition "(a free concurrency slot aside) … so host transitions cannot deadlock". A scope finalizer cannot be interrupted. A parent build that mounts a child in Effect.scoped and closes it while an operator restart of the child drains: the take-over waits for the restart's build, which waits for the slot the parent build holds. Round 8 added the wait for a build; finalizers used to wait only for stops, which take no slot.
Fix
In a finalizer wait only for the stop step and order the child's removal for after the owning operation, or count the limit from the meeting and include the slot wait; restate in 14, INV-BR-017, check 89 and INV-BR-030.

H2When the last applied manifest fails re-verification at the fresh→stale re-apply, requiresFresh entries are never disabled gapverified

Where
federation/behaviors/06-kill-path-placement-and-skew.md:544-566 vs 02-sync-offline-and-rebootstrap.md:266-272; ADR-FD-007:26
Evidence
06 lists "a freshness re-apply (BEH-FD-012)" among the re-applies whose refusal means "MUST NOT reconcile it … keep what runs"; only pending-kill and BEH-FD-042 disables act. 02: "On the transition from fresh to stale, the plugin MUST re-apply the same revision with fresh: false, so that every entry marked requiresFresh is listed with disabled: true." The likely trigger, a revoked authority signer, leaves a stale or capped host running every entry the authority marked unsafe on old instructions.
Fix
On a refused re-verification while stale, also disable each owned plugin the last successful projection marked requiresFresh, as pending kills are; add to check 34.

H3Replay runs a spawn for real, but nothing records or replays the subagent's model, so INV-AG-006 cannot hold gapverified

Where
agent/behaviors/05-agent-testing.md:133-136, :80-81, :237-239; 04-subagents.md:117-123; 01-agent-seams.md:591-592; INV-AG-006 (invariants.md:136-140)

H4The sequence companion's store-swap prepare reads through EventStore.readAll, which now awaits whenReadable, which a prepare must not await: the install deadlocks regressionverified

Where
sequence/behaviors/02-incarnation-and-verification.md:55-61, :68-72 vs event-store/behaviors/05-storage-port-and-acceptance.md:152-154; durable-bus/behaviors/06-replay-and-snapshots.md:626-643
Evidence
Sequence: a participant "whose prepare reads, from the store about to be replaced, every series", found by "adapter readAll with types". Event-store: "read and readAll … MUST await durable-bus DurableBus.whenReadable". Bus: "a prepare, run or apply MUST NOT await whenReadable, directly or through an event-store read, since it would wait for the install it runs in." Sequence was not changed in round 8.
Fix
Give participants an ungated read (a raw adapter read handed to prepare/apply, or an exemption for reads inside a running participant step) and have BEH-SQ-009 use it.

H5Event-store followers restarted on the OriginChange hold the SQLite write lock while awaiting whenReadable, so the bus's recordIncarnation retry never commits gapverified

Where
event-store/behaviors/05:152-154, :166-176, :205-208 (BEH-ES-035); durable-bus/behaviors/07-core-bus-and-adapters.md:255-256; 06:415-420, :471, :518-524, :634-639; 01-events-and-envelope.md:259-264
Evidence
A follower "MUST read its checkpoint from the store at the start of each batch transaction" and its readAll then awaits whenReadable inside it; the SQLite adapter takes the write lock at BEGIN IMMEDIATE. The OriginChange is emitted at the switch while origin-unrecorded may still hold, and "After the OriginChange, projections MUST restart". The lift needs recordIncarnation "in its own InboxStore.transaction" — the lock the follower holds. The bus's "fence first" escape covers event-store writes only, not follower batches.
Fix
Await whenReadable before a follower (projection, chain, sequence's post-change step) opens its batch transaction, restart projections only once it completes, and pass the fence-first duty on to readers inside their own transaction.

H6whenReadable gates only the start of an event-store read; a lazy read stream in flight across run/apply decodes a held subject in plaintext gapverified

Where
event-store/behaviors/05:152-158, :289, :41; 01-streams-and-append.md:265-266 vs keyring/behaviors/02-field-encryption.md:123-131, 03-shred-and-acceptance.md:479-485, keyring/invariants.md:51-56; durable-bus/06:300-301
Evidence
read: (r) => Stream.Stream<ReadEvent<unknown>, LoadError>, gated "before they read". Keyring: "no decode reaches it then, because every subscription, every follow and every event-store read waits". A stream begun before the freeze's second step keeps pulling pages through the drain, fetch, run and apply; follow interrupts a read in flight and discards its page, event-store reads do not.
Fix
Re-await whenReadable before each page, or interrupt event-store reads in flight at the end of the freeze's second step with a retryable failure; update checks 18 and 46.
