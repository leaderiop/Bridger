## Context

The gate has to find the ticket a call claims ([ADR-GX-010](../decisions/010-sign-first-then-call.md)), and a reviewer later has to join the signed approval to the host's record of the change (Part 11 §11.70). Core's `OperationRequest` carries `operation`, `target`, `definition`, `configChange`, `actor`, `reason` and `correlationId`; `correlationId` is always present, supplied by the caller or generated by the host ([BEH-BR-219](../../core/behaviors/25-operation-gate.md)). The `requested` and terminal records of the call carry the same `correlationId` ([BEH-BR-195](../../core/behaviors/23-audit-sink-and-record.md), [BEH-BR-224](../../core/behaviors/25-operation-gate.md)). Core declined a separate context field on the request for citing tickets ([ADR-BR-039](../../core/decisions/039-config-fingerprint-port.md), alternatives).

`reconcile` is one call that consults the gate once per entry action, each with its own request ([BEH-BR-201](../../core/behaviors/23-audit-sink-and-record.md), BEH-BR-222 of [25 — Operation gate](../../core/behaviors/25-operation-gate.md)).

## Decision

- **`correlationId` is the ticket id.** A call that needs approval is made with `correlationId` equal to the ticket's `id`. The issuer generates ticket ids that satisfy core's `correlationId` rules. The gate looks the ticket up by `request.correlationId` only; it reads no other field, header or ambient value to find it. A call with a host-generated `correlationId` finds no ticket and is refused with `no-ticket`, unless the policy exempts it ([ADR-GX-014](../decisions/014-deny-by-default-policy.md)).
- **One binding per request.** A ticket holds one or more bindings. `authorize` recomputes the binding digest from the request ([ADR-GX-012](../decisions/012-binding-contents.md)) and looks for an unconsumed binding of that ticket with an equal digest. No match refuses; the digest, not the position in the list, selects the binding.
- **Reconcile bundles.** For `reconcile`, the ticket is a bundle: one binding per entry action that the reconcile is expected to submit to the gate (install, replace, reconfigure, uninstall, and so on). Each gate consultation consumes exactly the one binding whose digest it matches. A binding is never shared between two entry actions, and one entry action never consumes two bindings.
- **Partial reconcile.** If a reconcile stops part-way (an entry refused, a build failure, interruption), the bindings already consumed stay consumed, and the unconsumed ones stay valid until the ticket's `notAfter`. A re-run of the same reconcile with the same `correlationId` submits only the actions still needed and consumes their bindings; actions already applied produce no gate call. A bundle binding left unconsumed at `notAfter` expires with the ticket. Checks on read report each consumed binding against its record and list the unconsumed ones ([RSK-GX-022](../gxp/03-risk-assessment.md#rsk-gx-022)).
- **The join.** The link between approval and change is the triple: `correlationId` (= ticket id), the binding digest recomputed from the `requested` or `rejected` record, and the ticket store's consumption event for that digest. `checkApprovals` reports `approvalWithoutRecord` or `recordWithoutApproval` when any element of the triple is missing or disagrees ([ADR-GX-007](../decisions/007-checks-never-claim-integrity.md)), and `linkApprovals` lays each consumed binding beside its record ([BEH-GX-087](../behaviors/11-signature-linking.md)).

## Alternatives considered

- **A ticket field in `reason`.** Rejected: `reason` is free text written by a person and is part of the binding when the policy binds it; parsing it would make a human sentence carry a key.
- **A new `approvalRef` field on the core request.** Rejected: core declined it, and `correlationId` already joins request and records without a core change.
- **One ticket per reconcile entry.** Rejected: a reconcile would need as many `correlationId`s as entries, which core does not support within one call.

## Consequences

**Positive**:

- Approval and record join on a field core already carries and records, with no core change.
- A reconcile can be approved as one reviewed set and still be checked action by action.

**Negative**:

- The caller must set `correlationId` deliberately; a forgotten one is a refusal, not an unlinked change.
- A bundle must anticipate the actions the reconcile will submit; an unexpected action is refused and needs a new ticket.

**Trade-off accepted**: a convention on an existing field and bundles that must be planned, in exchange for a join that needs nothing from core.
