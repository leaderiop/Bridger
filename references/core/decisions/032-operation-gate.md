## Context

In a GMP system some changes must be approved before they happen: replacing a plugin that computes release results, reconfiguring a batch-record module. Approval may require an electronic signature linked to the change (21 CFR Part 11 §11.50, §11.70, §11.200) and an authority check (§11.10(g)). Bridger's core does not and should not implement approvals or signatures ([ADR-BR-027](../decisions/027-core-exclusions.md)); the question is where a companion or consumer plugs them in.

The obvious answer — a companion that wraps `Host` and checks approval before delegating — is bypassable. `Bridger.Host` is a service key; any code that can resolve it, including application code, adapters, base services and plugins that list it in `requires`, holds the raw host. `install` returns a `PluginHandle` whose `remove` and `restart` act on the raw host. `reconcile` performs installs, replaces and removes internally, one per entry, where no wrapper can see them. A control that applies only to callers who choose to go through it is not a control.

[ADR-BR-020](../decisions/020-typed-event-bus.md) excluded veto hooks from the event bus, for reasons that still hold: a veto by event is plural, prioritised and failure-isolated.

## Decision

```ts
// illustrative — not type-checked
interface OperationGate { readonly authorize: (request: OperationRequest) => Effect.Effect<void, OperationRejected> }
// service @bridger/core/OperationGate, read once at construction with Effect.serviceOption
type OperationRequest = {
  operation: Operation; target?: { id: string; realm: string }; actor: Actor; reason?: string; correlationId: string  // always present: supplied, or generated by the host
  definition?: { version?: string; digest?: string }; configChange?: { paths: readonly string[] }
}
```

- **A port in core, inside the host.** The host consults `@bridger/core/OperationGate`, when wired, on every operator mutation, whichever path reached it: a direct `Host` call, a `PluginHandle` method or a `reconcile` entry. The core guarantees that the gate cannot be bypassed through the `Host` it guards.
- **Position.** The gate is step 5 of the eight-step order of a mutating call fixed in [22 — Attributable operations](../behaviors/22-attributable-operations.md) (BEH-BR-188): (1) `HostClosed`, (2) attribution, (3) audit-degraded latch, (4) validation, (5) gate, (6) `requested` record, (7) `WouldDeadlock` check, the turn at the plugin's linearization point, `WouldDeadlock` again, re-validation and legality, then intent and transition, (8) terminal record. That behaviour is the single statement of the order; this ADR does not restate it differently. The gate therefore always sees an attributed request for something that can happen, and runs before anything is recorded or changed.
- **Refusal changes nothing.** A refusal fails the call with `OperationRejected { operation, target, reason }` and, when a sink is wired, writes one `rejected` record. No intent is recorded and no transition runs.
- **Fail closed on gate defects.** A gate that dies, or fails or times out in any way other than a typed refusal, is treated as a refusal. An approval service that cannot answer has not approved. The bound is `BridgerOptions.gateTimeout` (default 60 seconds; `"forever"` only when declared), and the refusal reason is `"gate-timeout"` or `"gate-defect"`. Human approval is meant to be obtained *before* the call — the companion records the approval and the gate checks it — not by holding the call open while someone decides.
- **No default implementation, not even a permissive one.** Unwired, there is no gate and behaviour is unchanged. A provided allow-all gate would be a control that does nothing while appearing in the configuration as a control; that is the false compliance affordance Qadi ADR-QD-056 refused when it declined a no-op signature service.
- **System transitions are not gated.** Runtime failures, dependency-loss stops and revocations are consequences, not decisions; they are audited ([ADR-BR-030](../decisions/030-audit-sink-port.md)) but never asked for permission.
- **`reconcile` is gated per entry.** The gate is consulted once per entry action, not once for the batch; a refused entry appears in `ReconcileReport.rejected` and the others proceed ([ADR-BR-023](../decisions/023-desired-state-reconcile.md)).
- **No values cross the gate.** The request carries configuration paths, never values ([ADR-BR-033](../decisions/033-no-config-values-in-audit.md)).
- **This amends ADR-BR-020 for host lifecycle operations only.** The gate is a port, not an event; application events keep no veto over the host.

## Alternatives considered

- **A companion wrapper alone.** Rejected: bypassable through the raw `Host`, handles and `reconcile` entries, as above. A wrapper may still exist for ergonomics; the control is the port.
- **Veto hooks on the event bus.** Rejected in ADR-BR-020 and again here: plural, prioritised listeners with isolated failures cannot express one accountable decision.
- **A permissive default gate.** Rejected: it would be indistinguishable from a real control in configuration and in the trail.
- **Gate after the `requested` record.** Rejected: every refused request would leave a `requested` record whose outcome is a refusal of a change that was never permitted to start; gating first keeps the `requested` record meaning "authorised and about to run".
- **Gate system transitions.** Rejected: refusing a runtime failure does not stop it; it only makes the host lie about its state.
- **Fail open on gate defects.** Rejected: an outage of the approval service would silently disable approval.

## Consequences

**Positive**:

- Approval and e-signature capture have one seam that every mutation path passes through ([ADR-BR-034](../decisions/034-gxp-companion-scope.md)).
- Unwired, nothing changes ([INV-BR-026](../invariants.md#inv-br-026-an-unwired-sink-or-gate-changes-nothing)).

**Negative**:

- The guarantee covers the `Host` that the gate guards. Code that builds a second host, or reaches plugin services and their stores directly, is outside it; that is the consumer's access control.
- An unavailable approval service blocks all operator changes.
- The gate sits on every mutation's path and adds latency; a `reconcile` of many entries makes many authorisation requests.

**Trade-off accepted**: a port in core with no default, at the cost of a GxP-shaped hook in a general library, because a companion-only control would be bypassable and a default would be a control in name only.

**Amendments (2026-11-08)**:

- `OperationGate` is the `Gate<OperationRequest>` instance of [ADR-BR-047](../decisions/047-generic-gate-and-plan.md); port and records unchanged. A deferral at the host is a refusal; the approved change is re-issued and gated again.
