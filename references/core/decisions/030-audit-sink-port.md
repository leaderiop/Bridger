## Context

SPEC.md gives the host two observation channels, and neither is an audit trail. `Host.changes` is latest-wins: a slow subscriber skips revisions. `Host.events` is a sliding `PubSub` of `eventBuffer` entries: a subscriber that falls behind loses the oldest events and sees a gap in `seq`. Both are correct for dashboards and diagnostics, and both are wrong for a record that must be complete, because their design accepts loss to protect the host from slow consumers.

A trail of plugin-set changes needs the opposite trade: no record may be lost silently, and the host must not proceed with a change it cannot record ([ADR-BR-031](../decisions/031-audit-failure-policy.md)). Making the diagnostic feed lossless would let any slow dashboard stall the host; making the trail lossy would defeat its purpose.

Qadi ADR-QD-044 (An optional decision sink) added a write-only, optional port read through `Effect.serviceOption`, with an error channel of `never`: a decision sink must not be able to change a decision. Bridger takes the optional, write-only shape and deliberately reverses the error channel.

## Decision

```ts
// illustrative — not type-checked
interface AuditSink { readonly record: (r: AuditRecord) => Effect.Effect<void, AuditWriteFailed> }
// service @bridger/core/AuditSink, read with Effect.serviceOption
```

- **Optional.** The host reads `@bridger/core/AuditSink` with `Effect.serviceOption`, once, at construction; a sink provided later is not picked up. The `OperationGate` is read the same way ([ADR-BR-032](../decisions/032-operation-gate.md)). With no sink wired, behaviour is identical to a host without audit support, nothing claims an audit exists, and `HostSnapshot.audit` is `"unwired"`; with one wired it is `"wired"`.
- **Typed failure.** `record` fails with `AuditWriteFailed { message }`. Unlike Qadi's decision sink, a sink failure must change the outcome; the policy is [ADR-BR-031](../decisions/031-audit-failure-policy.md).
- **The record.** `AuditRecord` carries `schemaVersion: 1`, `recordId` (from `IdGenerator`), `hostId`, `auditSeq`, `timestamp` (from `Clock`, ISO-8601 UTC with milliseconds), `actor`, optional `reason`, `correlationId` (always present: supplied by the caller or generated by the host with `IdGenerator`), optional `causationId`, `operation` (an `Operation` or a `SystemTransition`), optional `target { id, realm }`, `phase` (`requested`, `rejected`, `completed`, `failed`, `superseded`, `joined` or `system`), `noop: true` for a no-op success, `before`/`after` (`state`, `version`, `digest`, `revision`), `configChange { paths }` ([ADR-BR-033](../decisions/033-no-config-values-in-audit.md)), `children` (for a reconcile parent: a count), `error { _tag, message }`, `endsIntentOf` (on an `intent-ended` record only: the `recordId` of the parked call's `requested` record), `resumes` (on the terminal record of a call that resumed a parked operation: the same kind of link), and `droppedSinceAck` (on `acknowledgeAuditDegraded` records only: records dropped for writer overflow since the previous acknowledgement).
- **Cardinality.** Each mutating call that reaches the `requested` step writes exactly one `requested` and exactly one terminal record (`completed`, `failed`, `superseded` or `joined`), except a call whose `requested` record is dropped because the writer queue is full, which fails at once and writes none (BEH-BR-198, BEH-BR-202). A call the `OperationGate` refuses writes one `rejected` record and no `requested` record, because it is refused before that step ([ADR-BR-032](../decisions/032-operation-gate.md)); a call refused for attribution or by the latch writes none. A joined call's terminal record links to the call it joined; `reconcile` writes a parent pair plus a pair per entry acted on, linked by `correlationId`. System transitions write one `system` record each.
- **Single writer, in order.** Records are written one at a time, in `auditSeq` order, from one serialisation point, with a bounded queue behind it and failed writes retried in place ([ADR-BR-031](../decisions/031-audit-failure-policy.md), [ADR-BR-037](../decisions/037-audit-sequence-separate-from-event-seq.md)).
- **No copy.** The core holds a record only until the sink accepts it and keeps no copy afterwards. The original record is the one handed to the sink; retention, storage, durability and review are the consumer's or the companion's ([ADR-BR-034](../decisions/034-gxp-companion-scope.md)).
- **Never the event stream.** `Host.events` remains a lossy diagnostic feed. No document, API name or log message describes it as an audit trail.

## Alternatives considered

- **Make `Host.events` the trail** (unbounded or back-pressured). Rejected: one channel cannot both refuse to drop records silently, as the trail must, and never block, as dashboards need; whichever guarantee loses, one audience is misled.
- **Derive the trail from `Host.changes`.** Rejected: latest-wins skips revisions, and snapshots carry no actor, reason or operation outcome.
- **Qadi's error channel `never`.** Rejected: a sink that cannot fail cannot report a lost record, and the host would proceed with a change that left no trace.
- **A required sink with an in-memory default.** Rejected: an in-memory default is a trail that disappears on restart, and its existence would let a deployment believe it has an audit trail it does not have.
- **Record from a companion wrapper around `Host`.** Rejected: a wrapper sees neither system transitions nor join, supersession and no-op outcomes decided inside the host.

## Consequences

**Positive**:

- A regulated user gets sequenced, attributed records of plugin-set changes, handed to a sink in order from the only place every change is visible; the losses core can cause (writer-queue overflow, records unwritten when the host closes, records still queued when the process dies, and a running `reconcile`'s parent record lost at shutdown) are stated, and those it can detect are signalled by the latch ([ADR-BR-031](../decisions/031-audit-failure-policy.md)); a close-flush loss arises after the close report, so it is signalled by the error log and by `Host.controls().closed` (`CloseTail`, [24 — Time, identifiers and sequence](../behaviors/24-time-ids-and-sequence.md), BEH-BR-212; CCR-BR-037): `lastWritten` below `lastNumbered` for a numbered record, and the latch, carried as `CloseTail.auditDegraded`, for a terminal, `rejected` or system record whether numbered or not; only a never-numbered `requested` record is signalled by the error log alone (CCR-BR-038).
- Unwired, the port costs one `serviceOption` read at construction and changes nothing else.
- The audit channel and the diagnostic channel keep their own guarantees, and the difference is stated, not implied.

**Negative**:

- An awaited sink sits on the operation's path; a slow sink slows every mutation, bounded by `auditTimeout`.
- The record schema is a public contract (`schemaVersion: 1`); changing it needs a versioned migration story in the consumer's store.
- The core cannot tell whether the sink stores anything. A sink that acknowledges and discards satisfies the port.

**Trade-off accepted**: an awaited, failure-typed port on every mutation, at the cost of latency, in exchange for a trail that, while the host runs, cannot lose a record without the host knowing.

**Amendments (2026-11-10)**:

- The record gains `onBehalfOf` ([ADR-BR-043](./043-plugin-principal-and-mandatory-policy.md)), `annotations` and `annotationsOmitted` ([ADR-BR-045](./045-operation-context-annotations.md)), `undoes` ([ADR-BR-051](./051-atomic-bundle-apply.md)), and `auditDropped`, `sanitized` and `requestedBy` (CCR-BR-026, CCR-BR-028). The field list above is the one first decided; the current shape is `AuditRecord` in [23 — Audit sink and record](../behaviors/23-audit-sink-and-record.md), BEH-BR-195.
- Cardinality: a call refused by the `RefusalList` at step 4b also writes exactly one `rejected` record and no `requested` record ([ADR-BR-053](./053-refusal-list.md)); the undo actions of an atomic `reconcile` write their own records under the parent ([ADR-BR-051](./051-atomic-bundle-apply.md)) (CCR-BR-034).
